# Архитектура аккаунтов, идентичностей и аутентификации

## 1. Основная модель

В системе существуют следующие сущности:

- **User** — аккаунт пользователя в приложении и владелец связанных с ним пользовательских данных.
- **Identity** — идентификатор субъекта во внешней или локальной системе, который может использоваться для аутентификации.
- **Contact** — контактные данные пользователя, которые сами по себе не предоставляют права входа.
- **Session** — состояние активного доступа, созданное после успешной аутентификации.

Эти сущности имеют разные обязанности и не являются взаимозаменяемыми.

Один **User** может иметь несколько **Identity** разных типов, например EmailIdentity, UsernameIdentity и GoogleIdentity, а также несколько **Contact**.

Наличие **Identity** само по себе не означает, что соответствующий способ входа включён или доступен. Это определяется правилами аутентификации приложения.

## 2. Инварианты модели

### 2.1. Принадлежность Identity

Каждая **Identity** принадлежит ровно одному **User**.

- **Identity** не может одновременно принадлежать нескольким **User**.
- **Identity** не может существовать без связанного **User**.
- Каждый **User** должен иметь хотя бы одну **Identity**.
- Один **User** может иметь не более одной **Identity** каждого типа.
- Идентификатор конкретного типа **Identity** должен быть глобально уникальным в пределах этого типа.

Если идентификатор уже используется **Identity** того же типа, это **конфликт**: вторая такая **Identity** не создаётся ни при регистрации, ни при **Link**. Поэтому **Merge** конфликта не встречает: две **Identity** одного типа с одинаковым идентификатором в системе существовать не могут.

### 2.2. Независимость Contact и Identity

**Contact** и **Identity** — разные сущности.

Наличие email или телефона в контактных данных **User** не создаёт автоматически соответствующую **Identity**.

Например, email, полученный от GoogleIdentity, не становится EmailIdentity без отдельного явно определённого процесса и необходимого подтверждения.

Удаление **Identity** не должно автоматически удалять отдельно сохранённые **Contact**.

### 2.3. Сохранение целостности

Любая операция над **User** или **Identity** должна сохранять все инварианты модели.

Операция не должна оставлять **User** без **Identity**, создавать несколько **Identity** одного типа у одного **User** или нарушать глобальную уникальность идентификаторов.

## 3. Операции над Identity и User

Операции **Link** и **Unlink** относятся исключительно к **Identity**.

Операции **Merge** и **Split** относятся исключительно к **User**.

Эти операции имеют разные цели и не должны подменять друг друга.

| Операция   | Объект операции | Назначение                                                                             |
|------------|-----------------|----------------------------------------------------------------------------------------|
| **Link**   | **Identity**    | Связать новую **Identity** с существующим **User**                                     |
| **Unlink** | **Identity**    | Удалить конкретную **Identity** из **User** и удалить её данные аутентификации         |
| **Merge**  | **User**        | Объединить несколько **User** в один                                                   |
| **Split**  | **User**        | Разделить один **User** на несколько, распределив между ними существующие **Identity** |

## 4. Link

**Link** — операция связывания новой **Identity** с существующим **User**.

<img src="./images/Account Operations_Link.png" alt="Link operation" width="400">

Операция выполняется после подтверждения владения соответствующей **Identity**.

Правила:

1. Если соответствующая **Identity** ещё не существует, она создаётся и связывается с целевым **User**.
2. Если **Identity** уже принадлежит целевому **User**, повторное связывание не выполняется.
3. Если **Identity** принадлежит другому **User**, операция **Link** не выполняется. Для объединения используется **Merge**.

**Link** не объединяет разные **Identity**, не объединяет **User** и не переносит контактные данные автоматически.

Наличие данных внутри одной **Identity** не создаёт другие **Identity** автоматически.

### 4.1. Подтверждение перед созданием Identity

**Identity** создаётся только после подтверждения владения её идентификатором. Для EmailIdentity это означает подтверждение доступа к адресу электронной почты, например одноразовым кодом.

Пока адрес не подтверждён, заявка на регистрацию не является **Identity** и не резервирует адрес.

### 4.2. Совпадение email не связывает Identity

Человек может войти через внешний провайдер (например, Google), и подтверждённый email, полученный от него, может совпасть с email существующей EmailIdentity какого-либо **User**. Это совпадение не доказывает, что новая **Identity** принадлежит этому **User**.

Совпадение проверяется только среди **Identity**. Данные **Contact** для этого не используются.

Такое совпадение между **Identity** разных типов — это **совпадение email**. Оно допустимо при создании любой **Identity** (регистрация, **Link**, **Merge**) и само по себе ничего не связывает. Один и тот же email у **Identity** одного типа не является совпадением email, а является конфликтом (см. 2.1).

В этом случае система:

- не должна автоматически связывать новую **Identity** с существующим **User**;
- не должна автоматически объединять **User**;
- может предложить войти в существующий **User** и после успешной аутентификации выполнить **Link** по правилам этого раздела.

Без такой аутентификации новая **Identity** остаётся отдельной и принадлежит собственному **User**. Объединение тогда возможно только через **Merge**.

## 5. Unlink

**Unlink** — операция удаления конкретной **Identity** из **User**.

<img src="./images/Account Operations_Unlink.png" alt="Unlink operation" width="400">

При успешном выполнении:

- выбранная **Identity** удаляется из системы;
- связанные с ней данные аутентификации удаляются;
- другие **Identity** того же **User** продолжают существовать;
- отдельно сохранённые **Contact** не удаляются автоматически.

**Unlink** не создаёт новый **User** и не переносит **Identity** другому **User**.

### Ограничение

Если выбранная **Identity** является последней у **User**, операция **Unlink** отклоняется.

Это необходимо, поскольку **User** не может существовать без хотя бы одной **Identity**.

Если требуется сохранить **Identity**, но перенести её к другому **User**, следует рассматривать **Split**, а не **Unlink**.

## 6. Merge

**Merge** — операция объединения двух или нескольких **User** в один целевой **User**.

<img src="./images/Account Operations_Merge.png" alt="Merge operation" width="400">

В результате успешного **Merge**:

1. Все **Identity** исходных **User** переносятся к целевому **User**.
2. Связанные пользовательские данные обрабатываются согласно правилам соответствующей предметной области.
3. Исходные **User** после успешного переноса всех **Identity** удаляются из числа активных **User**.
4. Целевой **User** сохраняет свой идентификатор.
5. Сами **Identity** и их данные аутентификации остаются самостоятельными сущностями.

### 6.1. Ограничения Merge

**Merge** разрешён только тогда, когда результат удовлетворяет всем инвариантам модели.

В частности:

- у целевого **User** не должно оказаться нескольких **Identity** одного типа;
- глобальная уникальность идентификаторов должна сохраняться;
- ни один исходный **User** не должен оставаться без **Identity** в ходе незавершённой операции;
- данные, связанные с исходными **User**, не должны теряться без явно определённого правила обработки.

Если у целевого и исходного **User** уже есть **Identity** одного типа, это конфликт типов, и **Merge** блокируется до его явного разрешения.

Система не должна автоматически объединять такие **Identity**, удалять одну из них или переносить между ними данные аутентификации.

### 6.2. Независимость Identity после Merge

**Merge** изменяет принадлежность **Identity** к **User**, но не объединяет сами **Identity**.

Например, если один **User** имеет EmailIdentity с паролем, а другой **User** имеет GoogleIdentity, после **Merge** обе **Identity** принадлежат целевому **User**, но продолжают использовать независимые механизмы аутентификации.

Пароль остаётся связанным с EmailIdentity, а аутентификация через OAuth/OIDC — с GoogleIdentity.

## 7. Split

**Split** — операция разделения одного **User** на два или несколько **User** посредством переноса выбранных **Identity** к новым **User**.

<img src="./images/Account Operations_Split.png" alt="Split operation" width="400">

В отличие от **Unlink**, операция **Split** не удаляет выбранные **Identity**.

При успешном **Split**:

1. Создаётся новый **User** с новым идентификатором.
2. Выбранные **Identity** переносятся от исходного **User** к новому **User**.
3. Не выбранные для переноса **Identity** остаются у исходного **User**.
4. Исходный и новый **User** должны иметь хотя бы по одной **Identity**.
5. Ограничение не более одной **Identity** каждого типа у одного **User** должно сохраняться.

**Split** выполняется только для явно выбранных **Identity**. Система не должна самостоятельно выбирать их на основании совпадений email, имени, телефона или других атрибутов.

### Пример

До **Split**:

```
User A
├── EmailIdentity
├── UsernameIdentity
└── GoogleIdentity
```

После **Split**:

```
User A
├── EmailIdentity
└── UsernameIdentity

User B
└── GoogleIdentity
```

GoogleIdentity продолжает существовать, но теперь принадлежит **User B**.

**Split** не должен выполняться как побочный эффект **Unlink**.

## 8. Authentication и credentials

Authentication отвечает за проверку владения конкретной **Identity** и создание **Session** после успешной аутентификации.

Каждая **Identity** является самостоятельным способом идентификации и может иметь собственный механизм аутентификации и собственные credentials.

Например:

- пароль EmailIdentity относится к EmailIdentity;
- пароль UsernameIdentity относится к UsernameIdentity;
- OAuth/OIDC-аутентификация относится к GoogleIdentity.

Несколько **Identity**, принадлежащих одному **User**, не обязаны использовать одинаковые credentials.

Операции **Link**, **Unlink**, **Merge** и **Split** не должны автоматически объединять или переносить credentials между разными **Identity**.

Изменение credentials не меняет принадлежность **Identity** к **User**, если отдельно не выполняется соответствующая операция над моделью.

## 9. Session и операции над User

**Session** создаётся после успешной аутентификации и связана с **User** и той **Identity**, через которую выполнена аутентификация.

Концептуально:

```
Session
├── user_id
└── identity_id
```

После **Merge** или **Split** принадлежность **Identity** к **User** может измениться. Поэтому система должна обеспечить согласованность **Session** с актуальной моделью.

Для каждой активной **Session** должно выполняться одно из условий:

- user_id соответствует текущему владельцу **Identity**, указанной в identity_id;
- **Session** отозвана.

При удалении **Identity** её связанные сессии должны быть завершены или отозваны. Сессии других **Identity** не должны автоматически завершаться без соответствующего правила.

**Session** и токены не являются частью сущности **User** или **Identity** и управляются отдельной логикой аутентификации.

## 10. Итоговые правила

1. **User** — аккаунт и владелец пользовательских данных.
2. **Identity** принадлежит ровно одному **User**. Каждый **User** должен иметь хотя бы одну **Identity** и не более одной **Identity** каждого типа.
3. **Contact** — отдельная сущность. Контактные данные не превращаются в **Identity** автоматически.
4. **Link** связывает новую **Identity** с существующим **User**. Если **Identity** принадлежит другому **User**, применяется **Merge**.
5. **Unlink** удаляет конкретную **Identity** из **User** вместе с её данными аутентификации. Последнюю **Identity** удалять нельзя.
6. **Merge** объединяет **User**, перенося их **Identity** к целевому **User**. Конфликты типов **Identity** должны быть разрешены явно.
7. **Split** разделяет **User**, перенося выбранные **Identity** к новым **User**. Каждый получившийся **User** должен иметь хотя бы одну **Identity**.
8. Authentication проверяет владение **Identity**, а **Session** фиксирует результат успешной аутентификации.
9. **Merge** и **Split** не объединяют сами **Identity** и их credentials.
10. Все операции должны сохранять целостность модели и согласованность **Session** с актуальной принадлежностью **Identity**.
11. **Identity** создаётся только после подтверждения владения её идентификатором. Ожидающая регистрация не является **Identity**.
12. Совпадение email или других атрибутов не связывает **Identity** и не объединяет **User** автоматически. Для объединения требуется **Link** после аутентификации либо явный **Merge**.

## 11. Возможные расширения

Правила разделов 1–10 зафиксированы для текущей версии модели. Приведённые ниже расширения в неё не входят и записаны только как направление дальнейшего развития.

### 11.1. Лимит Identity по типам

Вместо единого правила «не более одной **Identity** каждого типа у одного **User**» максимальное число **Identity** может определяться отдельно для каждого типа:

| Тип Identity                               | Максимум у **User** | Комментарий                                                                                                                                   |
|--------------------------------------------|---------------------|-----------------------------------------------------------------------------------------------------------------------------------------------|
| Внешние провайдеры (например, GoogleIdentity) | несколько           | Например, рабочий и личный Google-аккаунты. Собственных credentials у них нет, поэтому сложности они не добавляют.                            |
| UsernameIdentity                           | одна                | Несколько локальных логинов с разными паролями усложняют управление credentials.                                                              |
| EmailIdentity                              | одна                | Дополнительные адреса остаются **Contact**. Несколько подтверждённых адресов можно ввести позже отдельной функцией.                           |

Последствия этого расширения:

- Конфликты типов (6.1) остались бы только для типов с лимитом «одна». Для внешних провайдеров такие конфликты исчезают.
- Формулировки правил 2.1, 2.3, 7.5 и 10.2 изменились бы с «не более одной **Identity** каждого типа» на «не более допустимого для типа числа **Identity**».
- Глобальная уникальность идентификатора в пределах типа и требование, чтобы у **User** была хотя бы одна **Identity**, остаются без изменений.
- Credentials по-прежнему принадлежат конкретной **Identity** (раздел 8). Несколько EmailIdentity у одного **User** потребовали бы отдельного решения, потому что пароль тогда естественнее относить к **User**, а не к каждому адресу.
